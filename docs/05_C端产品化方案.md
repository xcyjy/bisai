# C 端产品化方案（含登录用户体系）

> 目的：把当前**竞赛 MVP（无状态、无登录、同步转换）**升级为**面向 C 端的真实产品**，供你和队友评审。
> 已定基调延续文档③：**Python + FastAPI 后端 / Vue 3 前端**。
> 本文档聚焦 MVP 之外**必须补全的工程能力**：用户认证、数据持久化、AI Infra 工程化、产品化、部署运维。
>
> ⭐ 一句话结论：登录注册不是难点（成熟方案多）；**真正的生死线是「异步任务化 + 成本控制」**——同步转换在真实 C 端必然超时，不做配额一个恶意用户就能刷爆 API 账单。

---

## 一、现状诊断（MVP 的硬伤）

| 维度 | 现状（MVP） | C 端产品要求 | 不补的后果 |
|------|------------|------------|-----------|
| 用户 | 无，接口裸奔 | 注册 / 登录 / 会话 | 无法绑定数据、无法计费、无法风控 |
| 数据 | 转换完即丢，不落库 | 作品可保存 / 列表 / 再编辑 | 用户一刷新全没，体验崩 |
| 转换 | **同步 HTTP** 一次性返回 | 异步任务 + 进度反馈 | Claude 多章转换几十秒~分钟，**HTTP 必超时**，钱花了结果还丢 |
| 成本 | 无任何限制 | 配额 / 限流 / 计费 | **一个人狂刷即可刷爆账单** |
| 安全 | `CORS=*`、无鉴权 | 鉴权 + 防滥用 + 密钥隔离 | 接口/密钥裸奔 |
| 内容 | 自测原创小说 | C 端 UGC | 盗版 / 违规内容 / Prompt 注入 |
| 观测 | 无 | 用量 / 延迟 / 失败率 | 既无法计费也无法优化 |

> 说明：文档③第五节明确把"用户账户/登录"列为 MVP **不做**项——这是对的，竞赛阶段应聚焦核心链路。本文档即承接这条"被砍掉的"productization 工作。

## 二、目标架构

```
┌──────────────────────────────────────────────────────────────────┐
│                      前端 (Vue 3 + Router + Pinia)                  │
│   登录/注册页  ·  工作台(转换+双栏编辑)  ·  我的作品  ·  账户/配额    │
└───────────────────────────────┬──────────────────────────────────┘
                       HTTPS / JSON · Bearer JWT
┌───────────────────────────────▼──────────────────────────────────┐
│                      后端 API 网关 (FastAPI)                        │
│   Auth 中间件(JWT校验) · 限流(slowapi) · 配额检查 · CORS 白名单      │
│   ┌────────────┬──────────────┬───────────────┬────────────────┐  │
│   │ /auth/*    │ /projects/*  │ /jobs/*       │ /account/*     │  │
│   │ 登录注册   │ 作品CRUD     │ 异步转换任务  │ 套餐/用量      │  │
│   └────────────┴──────────────┴──────┬────────┴────────────────┘  │
└─────────────────────────────────────│─────────────────────────────┘
        ┌──────────────┐               │ enqueue            ┌─────────────┐
        │ PostgreSQL   │◄──────────────┤                    │ Redis       │
        │ 用户/作品/   │               │                    │ 队列+缓存   │
        │ 任务/用量    │               ▼                    │ +限流计数   │
        └──────────────┘     ┌──────────────────┐          └──────┬──────┘
        ┌──────────────┐     │ Worker (Celery)  │◄────── 取任务 ───┘
        │ 七牛云 Kodo  │◄────┤ 跑转换 Pipeline  │
        │ 原文/导出文件│     │ (复用现有 app/)  │──► Claude / Haiku / 离线引擎
        └──────────────┘     └──────────────────┘     (按套餐分级路由)
```

**关键变化**：API 进程**不再直接跑转换**，只负责入队；真正的转换交给后台 **Worker**，前端通过任务状态/SSE 拿进度与结果。

## 三、用户与认证体系

### 3.1 登录方式（C 端国内场景）
| 方式 | 优先级 | 说明 |
|------|--------|------|
| 手机号 + 短信验证码 | P0 | C 端主流，转化率高（接七牛云/阿里云短信） |
| 邮箱 + 密码 | P1 | 海外/备用 |
| 微信扫码登录 | P1 | 国内 C 端强需求，需企业资质 |

### 3.2 会话方案
- **JWT 双 token**：`access_token`（15min，放内存）+ `refresh_token`（7d，HttpOnly Cookie）。
- 后端 `Depends(get_current_user)` 中间件统一校验，未登录接口直接 401。
- 密码用 `bcrypt`/`argon2` 哈希，**绝不明文**。

### 3.3 选型建议（别自己造轮子）
- 快速：**Supabase Auth** 或 **Authing**（自带短信/微信/邮箱，省 80% 工作）。
- 自建：`fastapi-users`（开箱即用的注册/登录/找回/邮件验证）。

## 四、数据库设计（PostgreSQL）

> ORM 用 **SQLModel**（pydantic 作者出品，和现有 pydantic 模型无缝）或 SQLAlchemy。

```sql
-- 用户
users (
  id            UUID PK,
  phone         TEXT UNIQUE,          -- 或 email
  password_hash TEXT,
  nickname      TEXT,
  plan          TEXT DEFAULT 'free',  -- free | pro | admin
  created_at    TIMESTAMPTZ
)

-- 作品（一篇小说 = 一个 project）
projects (
  id            UUID PK,
  user_id       UUID FK -> users,
  title         TEXT,
  original_work TEXT,                 -- 原著名
  source_uri    TEXT,                 -- 原文存对象存储的 key（大文本不进库）
  char_count    INT,
  created_at    TIMESTAMPTZ,
  updated_at    TIMESTAMPTZ
)

-- 剧本版本（支持编辑历史/回滚）
screenplays (
  id            UUID PK,
  project_id    UUID FK -> projects,
  version       INT,                  -- 同一作品多版本
  doc           JSONB,                -- 完整剧本 dict（meta/characters/scenes）
  engine        TEXT,                 -- offline-rules | claude:opus | claude:haiku
  is_valid      BOOL,
  created_at    TIMESTAMPTZ
)

-- 转换任务（异步）
jobs (
  id            UUID PK,
  user_id       UUID FK -> users,
  project_id    UUID FK -> projects,
  status        TEXT,                 -- queued | running | succeeded | failed
  progress      INT DEFAULT 0,        -- 0~100，"已转 N/M 章"
  engine        TEXT,
  input_hash    TEXT,                 -- 输入指纹，命中缓存直接返回
  error         TEXT,
  created_at    TIMESTAMPTZ,
  finished_at   TIMESTAMPTZ
)

-- 用量流水（计费 + 风控依据）
usage_logs (
  id            UUID PK,
  user_id       UUID FK -> users,
  job_id        UUID FK -> jobs,
  engine        TEXT,
  input_tokens  INT,
  output_tokens INT,
  cost_cents    INT,                  -- 估算成本（分）
  latency_ms    INT,
  created_at    TIMESTAMPTZ
)
```

> 设计要点：**大文本（原文/导出文件）走对象存储**，库里只存 key；剧本结构化数据用 `JSONB`，方便查询又复用现有 dict 结构。

## 五、API 设计

> 在现有 `/api/health` `/api/convert` `/api/export` 基础上扩展。`convert` 从"同步"改为"建任务"。

| 模块 | 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|------|
| 认证 | POST | `/api/auth/send-code` | 发短信验证码 | 否 |
| 认证 | POST | `/api/auth/login` | 验证码/密码登录 → 返回 JWT | 否 |
| 认证 | POST | `/api/auth/refresh` | 刷新 access_token | refresh |
| 认证 | POST | `/api/auth/logout` | 注销 | 是 |
| 账户 | GET | `/api/account/me` | 当前用户 + 套餐 + 剩余配额 | 是 |
| 作品 | GET | `/api/projects` | 我的作品列表（分页/搜索） | 是 |
| 作品 | POST | `/api/projects` | 新建作品（上传/粘贴原文） | 是 |
| 作品 | GET | `/api/projects/{id}` | 作品详情 + 最新剧本 | 是 |
| 作品 | PUT | `/api/projects/{id}/screenplay` | 保存编辑后的剧本（新版本） | 是 |
| 作品 | DELETE | `/api/projects/{id}` | 删除 | 是 |
| 转换 | POST | `/api/jobs` | **建转换任务**（入队）→ 返回 job_id | 是 |
| 转换 | GET | `/api/jobs/{id}` | 查任务状态/进度 | 是 |
| 转换 | GET | `/api/jobs/{id}/stream` | **SSE** 实时推进度+流式结果 | 是 |
| 导出 | GET | `/api/projects/{id}/export?fmt=yaml\|pdf\|fountain` | 导出 | 是 |
| 上传 | POST | `/api/files` | 上传 .txt/.docx/.epub → 解析为文本 | 是 |

**转换的异步交互流程**：
```
前端 POST /api/jobs {project_id}
  → 后端：配额检查 → 算 input_hash → 命中缓存?直接返回 : 入队 → 返回 job_id
前端 打开 SSE GET /api/jobs/{id}/stream
  → 持续收到 {progress:25,"第1/4章完成"} ... {status:"succeeded",screenplay:{...}}
```

## 六、⭐ AI Infra 核心（本方案的重头）

这是把 demo 变成"扛得住真实流量"的关键，也是最能体现工程水平的部分。

### 6.1 异步任务化（必做）
- API 进程只入队，**Celery / RQ + Redis** 后台 worker 跑转换（复用现有 `app/pipeline.py`，几乎零改动）。
- 进度：worker 每转完一章写回 `jobs.progress`，前端 SSE 订阅。
- 收益：解决同步 HTTP 超时；用户断网不丢结果；可水平扩 worker 应对高峰。

### 6.2 成本控制（C 端生死线）
| 手段 | 做法 | 收益 |
|------|------|------|
| **配额** | free 每日 N 次 / M 字，超额引导付费 | 防刷爆账单 |
| **模型分级路由** | free → 离线引擎 / `claude-haiku`；pro → `claude-opus` | 成本与质量分层。**现有双引擎设计已是雏形，扩成多档即可** |
| **输入去重缓存** | `hash(原文+参数)` 命中直接返回历史剧本 | 同一小说不重复烧钱 |
| **token 预算** | 转换前按字数预估 token，超预算提前拦截 | 防超长文本失控 |

### 6.3 容错（已有基础，再加固）
- 现有"在线失败自动降级离线"已实现 👍。
- 补：**重试 + 熔断**（连续失败 N 次，临时全切离线，定时探活恢复）。

### 6.4 可观测性
- 每次调用落 `usage_logs`：引擎、in/out tokens、成本、延迟、是否降级。
- 既是**计费依据**，也是**优化依据**（哪类小说慢/贵）。
- 进阶：Prometheus + Grafana 看 QPS / 失败率 / P95 延迟。

## 九、安全与合规

| 类别 | 措施 |
|------|------|
| 密钥 | `ANTHROPIC_API_KEY` 等只在后端/密管，**绝不进前端**；CORS 收紧到域名白名单 |
| 鉴权 | 全业务接口 JWT；敏感操作二次校验 |
| 限流 | `slowapi` 按用户/IP 限流，防爆破与刷量 |
| 内容审核 | C 端 UGC 接**七牛云内容审核**，拦截违规小说 |
| 版权 | 上传须勾选"拥有授权/公版/原创"声明（呼应文档①合规要求） |
| Prompt 注入 | 用户原文是数据不是指令；用 structured output + 系统提示边界隔离 |
| 数据 | 传输 HTTPS；用户作品按 user_id 强隔离，越权访问返回 404 |

## 十、分阶段路线图

```
Phase 1  能登录、能存（1~2 周）★先拿到"真应用"形态
  └ users 表 + JWT 登录注册 + PostgreSQL + 作品 CRUD + 前端登录页/我的作品
    交付：注册→登录→转换→保存→在"我的作品"再打开 的闭环

Phase 2  AI Infra 工程化（1~2 周）★最能体现工程水平
  └ Celery+Redis 异步任务 + SSE 进度 + 配额限流 + usage_logs 用量记录
    交付：转换不再超时、有进度条、超额拦截、可看用量

Phase 3  产品化（1 周）
  └ 文件上传(docx/epub) + 多格式导出(pdf/fountain) + 模型分级 + 输入缓存
    交付：体验完整、成本可控

Phase 4  上线（3~5 天）
  └ Docker 化 + 七牛云部署 + 内容审核 + 监控告警
    交付：可对外公测
```

> 节奏建议：**先做 Phase 1 拿到形态，再做 Phase 2 打底子**。Phase 1 的登录/CRUD 方案成熟、风险低；Phase 2 的异步+成本才是这类 AI 产品真正的护城河，也是答辩/面试的亮点。

## 十一、技术选型汇总

| 层 | 选型 | 理由 |
|----|------|------|
| 认证 | Supabase Auth / Authing / fastapi-users | 短信/微信/邮箱开箱即用 |
| 数据库 | PostgreSQL（Supabase 托管） | JSONB 存剧本 + 关系型强一致 |
| ORM | SQLModel | 与现有 pydantic 无缝 |
| 迁移 | Alembic | 表结构版本化 |
| 队列 | Celery + Redis（或 RQ） | 异步转换、进度、重试 |
| 缓存/限流 | Redis | 输入去重 + 限流计数 |
| 对象存储 | 七牛云 Kodo | 原文/导出文件（贴合实训营生态） |
| 实时 | SSE（Server-Sent Events） | 进度推送，比 WebSocket 轻 |
| 部署 | Docker Compose → 七牛云/云托管 | api+worker+pg+redis 一键起 |
| 监控 | Prometheus + Grafana（进阶） | QPS/失败率/P95 |

## 十二、风险与降级

| 风险 | 降级方案 |
|------|---------|
| Celery 引入太重，时间紧 | 退化为 FastAPI `BackgroundTasks` + DB 轮询，先跑通异步语义 |
| 短信/微信资质未就绪 | 先上邮箱+密码，手机号/微信后置 |
| 对象存储联调慢 | 原文先存 DB `TEXT`，量大再迁对象存储 |
| 成本估算不准 | 先按字数粗估 + 真实 tokens 回填校准 |
| PDF/Fountain 导出复杂 | 先保 YAML，PDF 用现成库（reportlab）兜底 |

> **保命原则（延续文档③）**：先保证"登录→转换→保存"主闭环跑通，异步/计费/导出增强往后排，**绝不让外壳工程拖垮已经跑通的核心链路**。
