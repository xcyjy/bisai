## 一、题目原文与硬性指标

> **题目三：AI 小说转剧本工具**
> 很多小说作者希望将自己的作品改编成剧本，请开发一款 AI 辅助剧本创作工具，降低改编门槛，提升效率。
> 要求：能将 **3 个章节以上**的小说文本自动转换为**结构化剧本（YAML 格式）**，让作者可以快速获得**可编辑、可进一步打磨**的剧本初稿。请额外写一篇文档，定义剧本的 **YAML Schema**。文档中需说明该 **Schema 的设计原因**。

## 二、业务背景：剧本 ≠ 小说

> 这是整个项目的认知基石。不懂这一点，做出来的就是"带引号的小说"。

### 2.1 根本差异
- 小说能写**心理活动、上帝视角、抽象议论**；
- 剧本**只能呈现镜头拍得到的东西**：看得见的**动作** + 听得到的**声音**。
- 小说里的"他很愤怒"，剧本里必须变成"他一拳砸在桌上"——这条铁律叫 **Show, don't tell（展示而非告知）**。

### 2.2 心理描写的三条出路（AI 最容易翻车的点）
凡是 `他想 / 他明白 / 他没想到` 这类钻进人物脑子的句子，剧本里只能：
1. 转成**台词**（说出来）；
2. 转成**旁白/独白 V.O.**（画外音）；
3. 直接**删掉**。
> ⚠️ 绝不能把心理描写当成普通动作照搬——这是衡量"转得专不专业"的关键。

### 2.3 剧本的基本结构单位
- **场（Scene）**：一个连续的"**时间 + 地点**" = 一场。时间或地点一变，就换场。**这是切分的核心规则。**
- **场景标题（Slug Line / 场头）**：行业标准格式 `INT./EXT. 地点 - 时间`
  - `INT.` = 内景（室内）；`EXT.` = 外景（室外）
  - 例：`INT. 咖啡馆 - 黄昏`

### 2.4 剧本的核心元素（我们的 Schema 就围绕这些设计）

| 元素 | 英文 | 作用 |
|------|------|------|
| 场景标题 | Scene Heading / Slug | 标明时空 |
| 动作描述 | Action | 描写画面里发生的事 |
| 角色名 | Character | 谁要说话 |
| 对白 | Dialogue | 台词 |
| 表演提示 | Parenthetical | 怎么说，如"（冷冷地）" |
| 旁白/独白 | V.O. / O.S. | 画外音、心理活动转化 |
| 转场 | Transition | CUT TO / 淡出 等 |

## 三、一段示例：小说 → 剧本（直观理解全流程）

### 原文
> 雨下了一整夜。林然推开咖啡馆的门时，已经是黄昏。**他没想到她真的会来**。苏晴坐在角落，冷冷地看了他一眼。"你迟到了。"她说。"路上堵车。"林然努力让声音平静，"你……还好吗？"她把一份文件推到桌子中央——那是离婚协议。**第二天清晨**，林然站在公司楼下的天桥上，明白有些东西凉了就再也热不回来了。

### 转换分析
| 原文 | 类型 | 处理 |
|------|------|------|
| 雨下了一整夜…黄昏 | 环境 | → 场头时间 + 动作 |
| **他没想到她真的会来** | 心理 | → 旁白 V.O. |
| 冷冷地看了他一眼 | 动作 | → 动作（可拍） |
| "你迟到了" | 对白 | → 对白（苏晴） |
| 努力让声音平静 | 怎么说 | → 表演提示 parenthetical |
| **第二天清晨**+换地点 | 时空变化 | → **切第 2 场** |
| 有些东西凉了就热不回来了 | 心理/议论 | → 旁白 V.O. |

### 输出（YAML 片段）
```yaml
scenes:
  - scene_number: 1
    heading: { int_ext: INT, location: 咖啡馆, time: 黄昏 }
    elements:
      - { type: action, text: "雨下了一整夜。林然推门而入。" }
      - { type: voiceover, character: 林然, text: "我以为七年足够忘干净，可心跳还是快了。" }
      - { type: action, text: "苏晴坐在角落，冷冷看了他一眼。" }
      - { type: dialogue, character: 苏晴, text: "你迟到了。" }
      - { type: dialogue, character: 林然, parenthetical: "努力平静", text: "路上堵车。你还好吗？" }
  - scene_number: 2
    heading: { int_ext: EXT, location: 公司楼下天桥, time: 第二天清晨 }
    elements:
      - { type: action, text: "林然攥着没签字的文件，城市在脚下苏醒。" }
      - { type: voiceover, character: 林然, text: "有些东西一旦凉了，就再也热不回来了。" }
```

**三个必带走的认知**：① 切场靠时空；② 心理活动转旁白/台词；③ elements 用**有序列表**（动作和对白交错，顺序=节奏）。

## 四、专业编剧的改编流程（我们的工具插在哪一环）

```
1. 通读 → 提炼【一句话故事 Logline】
2. 写【故事梗概 Treatment】（散文体）
3. 拆【分场大纲 Beat Sheet】（每场发生什么）   ← 工具核心
4. 填【完整剧本】（动作+对白）                 ← 工具核心
5. 反复【打磨 Polish】（节奏、台词、删戏）      ← 留给作者（=可编辑）
```
**关键定位**：我们做第 3、4 步自动化，输出"**初稿**"，第 5 步交给作者打磨。**不追求一步到位出成品**——专业工具都是"AI 出初稿 + 人打磨"。

## 五、用户与痛点（功能价值的依据）

用户 = **想把自己作品改成剧本的小说作者**。

| 痛点 | 我们的对策 |
|------|-----------|
| 不懂剧本格式（INT./EXT.、场头） | 自动套用标准格式 |
| 改编工作量巨大（几十万字） | AI 自动出初稿，省体力活 |
| 怕丢失原著精华 | 忠于原文 + 原文↔剧本对照 |
| 想反复修改 | 输出**可编辑的 YAML** + 在线编辑器 |

> 我们做的每个功能，都应能对应到上面某个痛点——这是答辩时的"价值论证"。

## 六、难点与边界坑（demo 能处理则加分，处理不了要诚实声明）

| 小说写法 | 为什么是坑 | 应对 |
|---------|-----------|------|
| 倒叙 / 闪回 | 时间线跳跃 | 识别"回忆/那年"，标 FLASHBACK |
| 大段心理独白/议论 | 无动作无对白 | 转旁白，或提示"需人工改编" |
| 多线并行叙事 | 几条线交织 | 按视角/地点分别成场 |
| 群戏（多人同时说） | 对白归属乱 | 人物表 + 上下文推断说话人 |
| 无引号对白（"他说要走"） | 抽不出台词 | 间接转直接，或保留为动作 |
| 风景长描写 | 全转动作很啰嗦 | 提炼关键可视元素，删冗余 |

> **诚实声明已知局限 = 体现想得深**，比假装"全能"更得分。

## 七、评估维度（答辩时"你怎么证明效果好"）

1. **情节保留率**：原著关键情节有没有丢
2. **对白还原度**：台词抽取、说话人归属是否正确
3. **格式合法性**：YAML 是否 100% 通过 Schema 校验
4. **切场准确率**：场分得对不对
5. **戏剧性**：心理描写是否正确转化（没把"他想"当动作）
6. **可编辑性**：作者拿到能不能直接改

> 哪怕只是"抽 20 场人工标注，切场准确率 85%"，也远胜"感觉不错"。

## 八、行业术语速查表（文档/答辩显专业）

| 术语 | 含义 |
|------|------|
| Logline | 一句话故事梗概 |
| Treatment | 散文体故事大纲 |
| Beat Sheet | 分场/节拍大纲 |
| Slug Line / 场头 | 场景标题（INT./EXT. 地点-时间） |
| Action | 动作描述 |
| Parenthetical | 表演提示（怎么说） |
| V.O. (Voice Over) | 画外音/旁白 |
| O.S. (Off Screen) | 人在场但不在画面的声音 |
| Transition | 转场（CUT TO / 淡出） |
| Fountain | 纯文本剧本标记语言（剧本界的 Markdown） |
| Beat | 最小情绪/剧情单位 |
| Show, don't tell | 用画面展示而非文字告知 |
